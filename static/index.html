Project Presentation: Token-Bucket Rate Limiter REST API

A complete architectural summary detailing design decisions, mathematical models, thread synchronization, and operational resilience designed for presentation to technical teams and stakeholders.

01

Problem & Algorithmic Strategy

Traditional fixed-window counters suffer from the boundary burst vulnerability (2x traffic spikes at window transitions). The token bucket algorithm resolves this through continuous rate shaping.

Tokens(t) = min(B, Tokens(t_prev) + Δt * Rate)
  • Accommodates burst traffic up to capacity B.
  • Smooths sustained throughput at Rate tokens/sec.
  • No discrete window resets or boundary loopholes.
02

Thread Safety & Concurrency

High-throughput backend services require low lock contention and strict atomicity to prevent race condition over-allocations.

RegistryLock -> Manages bucket allocation Bucket.lock -> Serializes same-key checks
  • Two-tier locking hierarchy maximizes parallel execution.
  • Independent keys execute 100% concurrently.
  • Proven by 50-worker thread test with zero state corruption.
03

Dynamic Policy Clamping

If an API gateway or admin modifies a tenant's rate or burst capacity in real-time, the bucket must update smoothly without exploits.

# Tokens refilled at old rate, clamped to new burst: bucket.tokens = min(new_burst, refilled_tokens)
  • Does NOT reset an exhausted bucket back to full.
  • Clamps gracefully if new burst is lower than current balance.
  • Applies new refill rate going forward.
04

Deterministic Testing with Injected Clock

Time-dependent algorithms usually suffer from slow or flaky tests when using real-time sleeps (time.sleep).

def __init__(self, clock: Callable[[], float] = time.monotonic): self._clock = clock
  • FakeClock allows advancing time instantaneously in pytest.
  • 39+ automated tests run and complete in ~1.2 seconds.
  • 100% code coverage across all business logic and API endpoints.
05

REST API Contract & Status Codes

Adheres strictly to modern API design standards for traffic limiting.

  • GET /health: HTTP 200 health probe.
  • POST /v1/limit/check: HTTP 200 for both Allowed and Denied (rate limiting is a valid decision, not an error).
  • HTTP 422: Strict Pydantic validation for negative rates, empty keys, or cost > burst.
  • Provides exact retry_after_seconds on denial.
06

Production Integration Checklist

Guidelines for integrating into larger production microservices:

  • Process-Local: Perfect for sidecars or single-process API proxies.
  • Distributed Deployment: For multi-worker clusters, swap in-memory dict with Redis Lua script token bucket.
  • Memory Management: Introduce TTL / LRU eviction for workloads with billions of ephemeral keys.
